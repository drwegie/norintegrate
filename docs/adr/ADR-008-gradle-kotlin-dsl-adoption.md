# ADR-008: Gradle Kotlin DSL Adoption

**Status:** Accepted
**Date:** 2026-03-14

## Context

The team's prior build tool experience is Maven, which was the standard in the Java 8 / Spring 3 ecosystem. Maven's declarative XML `pom.xml` is verbose but predictable, and its lifecycle phases are well-understood after years of use. Gradle was also familiar in its Groovy DSL form, but the dynamic nature of Groovy build scripts — no type checking, limited IDE autocomplete, string-based configuration — makes them fragile at scale.

Three options were evaluated:

- **Maven**: Familiar, but multi-project builds in Maven are cumbersome. The `pom.xml` inheritance model and lack of composable build logic makes the three-module structure (common, api, mcp) more verbose than necessary. Maven also lacks a clean way to share version catalogs without a BOM.
- **Gradle with Groovy DSL**: More flexible than Maven, but Groovy DSL build scripts are dynamically typed. IDE support is weaker, and typos in property names or task configurations fail at runtime rather than at authoring time.
- **Gradle with Kotlin DSL (`build.gradle.kts`)**: Statically typed, with full IDE autocomplete in IntelliJ IDEA. Configuration errors surface at sync time. The Kotlin DSL is now the default in new Spring Initializr projects and is the direction the Gradle ecosystem has moved.

For a multi-project build where configuration is shared across three modules, type safety and IDE assistance reduce the maintenance burden significantly. Version catalogs (`libs.versions.toml`) integrate naturally with Gradle Kotlin DSL, centralising all dependency versions in one file.

Spring Boot 4's `spring-boot-gradle-plugin` and Spring Dependency Management plugin both have idiomatic Kotlin DSL APIs.

## Decision

Use Gradle 8.x with Kotlin DSL (`build.gradle.kts` and `settings.gradle.kts`) for all build configuration. Dependency versions are managed in `gradle/libs.versions.toml`. Maven is not used.

## Consequences

- All build files are statically typed; renaming a configuration block or mistyping a property produces a compile error at Gradle sync, not a cryptic runtime failure.
- IntelliJ IDEA provides autocomplete and navigation in `.kts` files.
- Developers with only Maven experience must learn Gradle concepts (tasks, configurations, conventions), which is a one-time learning cost.
- The project follows the same build toolchain as new Spring Boot projects generated by start.spring.io.
